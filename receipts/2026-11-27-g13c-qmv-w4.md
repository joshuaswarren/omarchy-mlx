# DEC-06: uvec4 (W4) weight loads for the R2S8 Multi decode GEMV on G13C

Row: CARD-QUEUE DEC-06 — 16-inch M1 Max 4B decode, cut `QmmVecQ4`
register pressure and memory-issue overhead. Lane wAN, 2026-11-27.

## Change

`qmm_vec.comp` gains a `QMM_W4` fast-tile arm of the bf16 Multi
GEMV (`QmmVecQ4MultiSubgroupBF16R2S8W4Fast`, same `R2S8` columns as the
shipped `R2S8W2Fast`): each lane owns one `uvec4` — two adjacent uvec2
pairs, 32 q4 values — per weight row per iteration instead of one
uvec2 pair. Per unit of work this halves the iterations, the
weight-load count, and the scale/bias epilogues. The group-to-lane
split changes from 4 lanes per scale group to 2, so the fp32
subgroup-add re-associates; bit-exactness is decided by screens, not
by construction. Selection is opt-in under `MLX_OMARCHY_Q4_W4=1`, only
where the kernel would be `R2S8W2Fast` (or `UpfrontFast`), only with
`K % 1024 == 0` and every member `N % 8 == 0`; the ≤3-member groups
keep `R2S8W2Fast3w` (UPFIFO). `K % 512`-only shapes never dispatch W4.

## Kernel screens (bf16 bits, candidate vs shipped W2-fast build)

- Same source, same defines, `-DQMM_W4=1` as the only candidate delta;
  the screen harness asserts the two SPIR-V blobs differ (W2 69,748 vs
  W4 100,692 bytes under this box's glslc) before any number counts.
- Apple GPU (G13C), `tools/q4-bw-bench --gap --2b --quick`, two legs,
  four passes total: the candidate arm ran every pass without error.
- The gap-mode screen carries no per-shape bf16 compare in this bench
  build; the default-mode screen cannot host the production shader
  (its descriptor tables are written for the vendored pre-multi base
  copy, and a base-override control with identical defines also
  reproduces full mismatch, so the compare plumbing, not the kernel,
  is what those screens would measure). The kernel-level bit contract
  for any future W4 work is the greedy-digest parity across the
  toggle, on a wheel that ships the kernel. Not checked here; see the
  verdict.

## Decode-mix bandwidth (Apple GPU, G13C, widedep 24-layer-set mix, medians)

| build | layer time | mix bandwidth | passes |
|---|---:|---:|---:|
| shipped `R2S8W2Fast` (base) | 181.2 µs | 284.0 GB/s | 2 legs, 2 passes each |
| W4 candidate | 194.8 µs | 264.1 GB/s | 2 legs, 2 passes each |

W4 is **-7.2 percent mix bandwidth** against the shipped kernel
(264 vs 284 GB/s, spread under 0.3 percent across passes). The
shipped kernel already streams the 2B decode mix at 284 GB/s; the
159 GB/s per-shape figure the row quoted predates the current
fast-tile state. Doubling the per-lane weight width doubles the
redundant x-quad loads per byte streamed, and the x re-reads dominate
issue slots on this part, which is exactly the direction W4 pushes
harder.

## Verdict

Proved negative. The W4 arm loses the bakeoff on the hardware the row
names and does not merge: the losing kernel is stripped from this
branch (history keeps it on the lane branch), selection was never
defaulted, and the row closes on the proved-negative receipt this
file carries. The model-level 5-pair ABBA is skipped by that gate: a
-7.2 percent QMV-mix result bounds any end-to-end tok/s outcome to a
loss, and a slower kernel has no bit-contract to pin.

## What merges

The bench fixes this row forced out, all found against real screens:

1. `--inc`, `--base-src`, `--base-defs` so both sides can compile the
   production shader with its shipped build defines (the vendored
   `qmm_vec_base.comp` copy has drifted threefold from production and
   no longer represents any shipped kernel).
2. The candidate side now rides the overridden base build plus its own
   delta. Found by a control screen: with the old plumbing, identical
   base and candidate defines produced a full-mismatch compare on one
   host and a clean-looking compare on another — a false-pass path
   that would have waved this row's kernel through.
3. `run-w4-dec06.sh`, the repeatable screen script (Apple-ICD pin for
   hosts that also expose a discrete card, different-blob guard,
   gpu-turn wrapper, eligible-shape verdict split).

## Not checked

- AGX register/occupancy counts: `AGX_DEBUG=shaderdb` produced no dump
  lines on this driver build (the debug-enabled bench runs also
  bus-errored or took SIGINT, so the dump leg is opt-in and was not
  chased further).
- The model-level ABBA and the parity digest: skipped by the negative
  verdict above, and the wheel build they need is disk-blocked on the
  host anyway (20 GB free against the 30 GB floor).
- Metal `qmv_fast` register comparison: no readable counter on this
  side of the boundary; the bandwidth screen against the shipped
  kernel is the instrument this row used.
