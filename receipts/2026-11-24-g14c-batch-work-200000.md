# Receipt: G14C batch-work 200000 — one submit per decode token on M2 Max

Date: 2026-11-24. Lane: wAX (PAR-63).

## Claim

The G14C (M2 Max) `batch_work` row moves 100000 to 200000. At 100000 the
mid-eval work-budget flush split every Qwen3.8-9B decode token into two
submissions (~181 of ~357 dispatches each); at 200000 the whole decode
step records into one command buffer and one queue submission.

## Mechanism

`eval.cpp` calls `batch_over_budget(nodes, batch_work, budget,
batch_work_budget(device_name))` per recorded node and commits the open
batch when the summed dispatch work-group count reaches the per-board
budget. The `generate_step` loop already evaluates one graph per token
(`omarchy_finalize_calls` = 0.984 per token measured), so a token whose
summed work-groups exceed the row produces two `vkQueueSubmit` calls.
The G14C row at 100000 bisected the 9B token; the split is inside the
eval — `MLX_OMARCHY_DEFER_COMMIT=1` left submissions at 1.969/token.

## Bound argument (#19)

At 100000 the row bounded one submission's summed work-groups to roughly
the calibrated ~6 ms p50 band; at 200000 the worst-case bound doubles to
about 12 ms of submission GPU time for the same dispatch mix — still
under a 33.3 ms frame and far under the ~78 ms #19 stutter threshold.
The per-dispatch wrongness threshold measured on this board sits between
87 ms and 152 ms for a single dispatch
(receipts/2026-10-10-m2-long-dispatch-vs-animating-window) and is not
moved by submission merging. The measured merged decode submission is
one whole 9B step at ~5.7 ms GPU busy per token (PAR-63 split diag), so
the calibration's own intent — submissions inside the 2-6 ms band for
decode — is preserved on the workload it was measured on.
