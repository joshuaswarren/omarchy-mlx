## qwen3 dense rope-norm fold, default ON (+4.18..+4.86% decode on the 4B)

`scripts/patch-mlx-lm-qwen3-rope-norm.py` folds the per-head q/k RMSNorm
into `mx.fast.rope_rms_norm` at the qwen3 dense attention site (the F3
fold ported to the dense file shape; removes 72 norm dispatches/token on
the 4B). Kill switch `MLX_OMARCHY_ROPE_NORM_FUSE=0`. Bit-exact: 24/24
iso bitcheck legs and greedy digests identical to the serving pins on
every A/B arm at every depth (e2c919be / 1bb7ff66 / c9480d81 / fff6d03b
— receipts/2026-10-04-jw16-decode-dispatchfuse.md). Paired alternating
A/B on jw16 (5 pairs per cell, idle-gated):

| depth | ctl tok/s | fold tok/s | paired delta |
|---|---|---|---|
| d64 | 64.22 | 67.29 | +4.71% |
| d128 | 63.59 | 66.69 | +4.86% |
| d256 | 62.19 | 65.05 | +4.60% |
| d512 | 56.47 | 58.85 | +4.18% |

**Installer wiring (the v0.7.15 defect class, caught at the draft gate):**
`apply-mlx-lm-patches.sh` did not invoke the patcher — a fresh install
would have shipped without the fold. Fixed in `c7ef91b9d`; new
`PatcherCoverageTests` fail when any `scripts/patch-mlx-lm-*.py` is
neither invoked by the apply script nor classified with a reason, and
when an invoked patcher would be missed by the installer's
derive-from-the-script fetch grep. Proven both directions (41 contract
tests OK with the wiring; the coverage test fails naming exactly
`patch-mlx-lm-qwen3-rope-norm.py` when the line is removed).
Fresh-install proof on the shipped bytes (jw16 gpuwin, FOLDCHECK):
fresh venv from the draft assets → installer fetch path from the tag
pulls the patcher → apply marks `qwen3.py` → d64 greedy digest
`e2c919be0fe285c6…` on the default arm AND under `FUSE=0` (bit-exact),
`rope_rms_norm` call counter 72 (default) vs 0 (negative control),
argmax identical.

## qmm prefill rasterization default: group-of-GM=4

`4d717225b` + `b9a759a75` (receipts `2026-10-03-prefill-axes/`): the
32-row `QmmPrefillCoopmatBF16X32[FullN]` route defaults to group-of-4
rasterization for multi-row-tile grids; `MLX_OMARCHY_QMM_NO_RASTER=1`
opts back. Bit-identical by construction (ascending-k f32 accumulation
untouched). Prefill tok/s vs the shipped default — jwm1 (G13G): 2B
pf512 +1.0% / pf1024 +1.3%, 4B pf512 +2.1% / pf1024 +0.8%, 9B pf512
+3.4% / pf1024 +3.2%; jw16 (G13C): 2B pf512 +1.0% / pf1024 +2.4%, 9B
pf512 +4.4% / pf1024 +3.6%. No cell regressed on either chip.

## GDN raw-route enablement (opt-in; default unchanged in v0.7.25)

`27b6904ed` + `d547f112b` + `bc51a7bd4`: the raw-gates decode kernel
accepts F32 A_log via flag bit 9 (f32 softplus matching the C++
fallback); `scripts/patch-mlx-lm-gdn-raw-repeat.py`
(`MLX_OMARCHY_GDN_RAW_REPEAT`, default 0) is an opt-in repo-only helper.
bf16-A_log models take byte-identical paths (bit 9 unset). Not wired
into the installer; the v0.7.25 release kept the existing behavior. The
default-on state announced in v0.7.26 is corrected by the v0.7.27 audit:
so the route is off by default.

## Wave-sched encoder commits reverted before the cut

The c7ef91b9d lineage briefly carried `b797627b0`/`10cc0487c` (wave
scheduling, default OFF). The packaged-worker gate caught the code
corrupting the GC lifecycle of mlx arrays in its DEFAULT path: g7c died
SIGSEGV in `_PyObject_GC_New` during traceback creation (coredumpctl
95881, SEGV_MAPERR), and a pristine fresh-dir rebuild reproduced it as
`PyObject_GC_Track: object already tracked` on an array created by
plain `mx.ones` in the worker CLI (exit 134). Bisect: v0.7.24 assets
PASS and the 7b569afab wheel PASSES the identical gate/host/driver/
window. Reverted in `b16f8f978` (overlay surface only; tools/bsched
kept). Nothing shipped. Wave scheduling returns only after the
lifecycle bug is fixed and the packaged-worker verify passes; its
default-ON flip stays blocked.
