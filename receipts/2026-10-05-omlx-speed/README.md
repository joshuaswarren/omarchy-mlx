# oMLX Linux speed profile — Qwen3.8-2B 4-bit

Owner: OmlxSpeed. oMLX pin: 0.7.0 / 4d4f5a28. Linux profile: private lab notebook, OmlxSpeed, 2026-10-05; macOS reference: private lab notebook, OmlxSpeed, 2026-10-05.

## Result

The requested positive macOS margin was not established on the M1 Ultra. The post-Metal-Toolchain rerun used the same 443-token Coreglass prompt and 128 generated tokens. Single-run results: plain mlx-lm 121.6 decode tok/s / 236.8 ms TTFT; oMLX 0.7.0 upstream server, no-cache, 110.7 / 241.4; mlx-lm +series overlay 81.7 / 436.8; oMLX +series overlay, no-cache 107.9 / 244.3. Prefix-cache on gave 75.5 / 445.7 cold and 75.0 / 451.7 warm. The prior run measured mlx-lm +series at 118.3 / 240.3 and oMLX +series at 105.0 / 251.3. The mlx-lm overlay result reversed sharply between runs, so these one-shot rows do not establish a stable speed advantage or a repeatable effect from the rebuilt Metal kernels.

On the M1 Max Linux system, mlx-lm +series in-process measured 88.2 tok/s and 390.2 ms TTFT at 443 prompt tokens. oMLX +series-overlay HTTP server measured 82.1 tok/s and 410.5 ms TTFT at 443 tokens; cache-on measured 81.8 tok/s and 412.6 ms. The server's own completion log reported 88.0 tok/s for its 128-token request; client TTFT/decode include API and stream overhead. Direct EngineCore generated 128 tokens at 90.95 tok/s / 546.17 ms TTFT using a separately tokenized 460-token prompt, so it is not a controlled comparison. Cache on/off changed client throughput by 0.3 tok/s and TTFT by 2.1 ms.

## Missing Linux gate

The measured Coreglass venv contained no omlx/_compat_gate.py. Direct probe reported mlx 0.32.4.dev202610050725+5c15fba, mlx-lm 0.31.4.dev0, oMLX 0.7.0, and mx.metal.is_available() = False. Its Qwen custom-kernel sources still gate on that Metal predicate: qwen35_gdn_prework.py:1801, qwen35_gdn_chunked.py:48, qwen35_moe_routed_decode.py:959, and qwen35_fa256_attention.py:160. Those routes remain closed on omarchy-mlx in this environment.

The repository's packaging/omlx-linux/patches/01-add-compat-gate.patch adds the Vulkan-aware custom_kernels_available() canary. 02-gate-sites.patch switches 16 mx.metal sites, including the Qwen GDN/MoE/FA256 and A26 JIT gates, to that canary. The Coreglass venv was not built by packaging/omlx-linux/install.sh: the run loaded the mlx-lm overlay, but not the oMLX compatibility patch. The measured timings do not establish the effect of these patches; rerun with the supported installer and verify canary success before comparing speed.

Server logs show generic sdpa256 attention and the qwen3_5 ragged-decode fallback wrapper applied. They show no ragged threadgroup-limit refusal/fallback or compile failure. Wrapper installation does not prove its kernel path ran. The 33,871 direct dispatch records use numeric IDs and do not separate prefill/decode or identify kernel families. The earlier client cProfile recorded socket/readiness wait, not server CPU. A separate server generation-step profile recorded 131 `GenerationBatch._step` calls (0.922 s self, 1.310 s cumulative) and 0.491 s cumulative in the Qwen35 model-call subtree; these timings do not attribute device execution time.

## M2 root cause and fix (2026-10-06)

Paired cProfile tables — direct `generate_step` profiled with the same per-step method as the server `GenerationBatch._step` — split the server-versus-direct gap. The server runs oMLX's own MTP-patched Qwen3.5 model (`omlx/patches/mlx_lm_mtp/qwen35_model.py`), whose `GatedDeltaNet` routes every chunk through `_process_chunk`'s composed chain: `nn.Conv1d` + `nn.silu` + `normalize_qk` as separate dispatches, 18 GDN layers per decode step. Direct mlx-lm takes the omarchy series' fused route — one `mx.fast.gdn_conv_update` dispatch folding conv1d, the silu activation, and the q/k `rms_norm_scaled` pair — so its per-step profile shows those calls only during prefill (18 calls total versus 18 per step). Both sides already share the same fused `gated_delta_update_raw` decode route; only the conv chain diverged.

Eliminated hypotheses with measurements: SSE/GIL contention (`stream_interval` forced 1 versus 16 through a runtime hook: server-internal 87.1 versus 87.1 tok/s — null), and the QuantizedLinear wrapper stack (CPU microbenchmark: the process-global fast-gate variant changed per-call cost from 0.665 to 0.678 µs — null; the earlier 1.04 ms/step estimate came from cProfile per-call inflation of about 1-2 µs and was withdrawn with its patch files).

Fix: `packaging/omlx-linux/patches/0006-omlx-q35-decode-conv-fuse.patch` adds the series' fused branch to `_process_chunk` with the same gates as the mlx-lm side (S==1, bf16, GPU default device, `hasattr` guard; qk-fold conditions head_k_dim==128, widths %256; kill switch `MLX_OMARCHY_OMLX_CONV_FUSE=0`; `lengths` and multi-token chunks keep the composed chain, so MTP verify and rollback replay are untouched). Contract test `packaging/omlx-linux/test_omlx_q35_conv_fuse.py` on the M2 GPU wheel: the fused-route test fails on the unpatched tree and passes on the patched tree (4/4), with fused output bit-equal to composed. `ast_import_scan` and the 9 `test_compat_guards` checks pass on the patched tree; the patch applies clean to the v0.7.0 pin.

Five-pair A/B (server restart per arm, `PYTHONPATH` shadow for the patched tree, CPU/PSI quiet gates 21/21 valid, all ten completion texts matching `b819a5ece9d2…`): server-internal decode 87.0 tok/s median before (range 86.8-87.2) versus 93.0 after (range 92.8-93.1), +6.9%, distributions fully separated; server TTFT 0.54 versus 0.52 s median; client aggregates 62.19 versus 66.55 tok/s. The server now reaches 96% of same-venv direct (93.0 versus 96.9 tok/s), up from 89.8%. Residual gap candidates for a follow-up ticket: the server-side `qwen3_next.py:224` layer call costs about twice the direct per-call time in the paired tables, and the oMLX layer wrappers carry ~578 extra `getattr` calls per step.

## Rejected M2 greedy-head experiment

The five-pair exploratory attempt is not performance evidence: its candidate changed token output, and concurrent build/CTS work ran on the M2. The previous load1-based gate was invalid because load1 includes earlier ticket activity; do not use those timings.

The failed guard had been too strict for oMLX's `omlx.utils.sampling` temperature-zero lambda; a wider guard entered the fused head but changed output. Both the patch and its installer registration were removed.

A separate candidate changed only `mx.eval(inputs, self._current_logprobs)` to `mx.eval(inputs)` in the mlx-lm 0.32 line. Its M2 five-pair run matched the expected completion-text and ordered token-ID hashes; top IDs matched exactly and top-logprob deltas stayed within 1e-5. All 21 CPU/PSI gate records were valid. Median client decode fell from 66.03 to 64.82 tok/s (-1.83%); median TTFT rose from 466.33 to 500.52 ms (+7.33%).

Measurement-frame correction (2026-10-06): the client decode medians are aggregate rates that include TTFT, so the TTFT shift alone reproduces the client delta. The server's own completion lines for the same ten requests report before 87.0 tok/s (range 86.9-87.1) versus after 86.9 (86.9-87.0): the candidate did not change server-side decode at all. Its real cost is TTFT +20 ms median (444 to 464 ms server-reported; client-side 466 to 500 ms including client overhead), not decode throughput. The verdict (reject) stands; the magnitude was misattributed. The pairs restart the server per arm, so every pair request is the first real request on a cold prefill graph: pair TTFT 444-464 ms versus 330-360 ms on a warm single server; client aggregate rates on this harness read ~66 tok/s against 85-87 server-internal for the same requests. Server-internal rates are the comparable metric going forward; client aggregates only compare like-for-like within one harness. The first queued attempt produced no measurements because its `vmstat` parser selected `wa` instead of `id`; the gate now locates `id` by header name. Raw results and parity traces are in private lab artifacts `artifacts/OmlxSpeed/20261006T043851Z-m2-speed/`.
