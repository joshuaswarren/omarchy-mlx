# 13-inch M1 (G13G) submission budget: 20000 to 35000

Date: 2026-11-27. Hardware: 13-inch M1 (`Apple M1 (G13G B1)`, 8 GPU cores, 16 GB unified memory), Linux `7.3.0-2-20261110.1-lab-ARCH`, pinned Mesa `53ad9af196f5`, `MLX_OMARCHY_DEFER_TOKENS=0`. All runs executed exclusively one-at-a-time under the GPU queue lock with zero GPU timeouts and zero foreign GPU usage.

## Question

At the prior `G13G` work budget of `20000` (`receipts/2026-11-21-g13g-batch-work-20000`), `Qwen3.8-2B-mlx-4Bit` decode at `ctx=512` and `ctx=2048` splits its 125 dispatches across `2.0` submissions per token (`9.93 ms` + `9.92 ms`). After fused decode kernels reduced per-token dispatch counts from `867` to `125`, can `G13G` run `2B` decode in `1.0` submission per token without raising `Qwen3-4B-Instruct-2507-4bit` decode submission `p99` above `33 ms`?

## Verdict

Raise `kBatchWorkCalibration` for `G13G` from `20000` to **`35000`**.

- `35000` is the smallest swept budget that brings both `Qwen3.8-2B` (`ctx=512` and `ctx=2048`) from `2.0` down to **`1.0` submission per token** (`32000` still splits at `2.0` submits/token).
- On `Qwen3-4B-Instruct-2507-4bit` (`63` isolated decode tokens), `35000` reduces submits/token from `5.0` to **`3.0`** while keeping decode submission `p99` well below `33 ms`:
  - `4B@512` decode: `p50 = 18.122 ms`, `p95 = 19.533 ms`, **`p99 = 20.581 ms`**, `max = 25.896 ms` (`40000` reached `p99 = 24.347 ms`, `max = 27.608 ms`).
  - `4B@2048` decode: `p50 = 20.030 ms`, `p95 = 22.839 ms`, **`p99 = 23.048 ms`**, `max = 27.845 ms` (`40000` reached `p99 = 26.082 ms`, `max = 31.496 ms`).
- Every tested model and context produces bit-identical greedy token IDs matching macOS 27.0 (`mlx 0.32.2`).
