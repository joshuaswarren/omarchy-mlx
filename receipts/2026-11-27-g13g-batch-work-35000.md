# 13-inch M1 (G13G) submission budget: `{35000 decode, 20000 prefill}`

Date: 2026-11-27. Hardware: 13-inch M1 (`Apple M1 (G13G B1)`, 8 GPU cores, 16 GB unified memory), Linux `7.3.0-2-20261110.1-lab-ARCH`, pinned Mesa `53ad9af196f5`, `MLX_OMARCHY_DEFER_TOKENS=0`. All runs executed exclusively one-at-a-time under the GPU queue lock with zero GPU timeouts and zero foreign GPU usage.

## Question

At the prior `G13G` work budget of `20000` (`receipts/2026-11-21-g13g-batch-work-20000`), `Qwen3.8-2B-mlx-4Bit` decode at `ctx=512` and `ctx=2048` splits its 125 dispatches across `2.0` submissions per token (`9.93 ms` + `9.92 ms`). After fused decode kernels reduced per-token dispatch counts from `867` to `125`, can `G13G` run `2B` decode in `1.0` submission per token without raising `Qwen3-4B-Instruct-2507-4bit` decode `p99` above `33 ms` **and** without regressing `4B` prefill submission tails?

## Verdict

Set `G13G` in `kBatchWorkCalibration` to **`{"G13G", 35000, 20000}`** (decode budget `35000`, prefill budget `20000` whenever an open batch records a multi-token prefill/tiled-matrix kernel via `is_prefill_work_kernel_name`, plus `dispatch_qmm_tile` slicing):

- **`35000` decode** is the smallest swept budget that brings both `Qwen3.8-2B` (`ctx=512` and `ctx=2048`) from `2.0` down to **`1.0` submission per token** (`32000` still splits at `2.0` submits/token).
- **`20000` prefill cap** eliminates the `4B` prefill tail regression that an unsplit `35000` cap introduced (`4B@512` prefill `p99` `67.26 -> 46.08 ms`, all-submits `p99` `45.60 ms` vs `45.34 ms` baseline; `4B@2048` prefill `p99` `128.36 -> 84.03 ms`, all-submits `p99` `83.31 ms` vs `83.04 ms` baseline).
- On `Qwen3-4B-Instruct-2507-4bit` (`63` isolated decode tokens), decode drops from `5.0` to **`3.0` submits/token** while keeping decode `p99` well below `33 ms`:
  - `4B@512` decode: `p50 = 18.223 ms`, **`p99 = 21.532 ms`**, `max = 23.542 ms` (`<= 33 ms`).
  - `4B@2048` decode: `p50 = 20.004 ms`, **`p99 = 21.572 ms`**, `max = 28.328 ms` (`<= 33 ms`).
- Every tested model and context produces bit-identical greedy token IDs matching macOS 27.0 (`mlx 0.32.2`).
- Sibling boards leave `prefill_budget = 0` and keep identical decode and prefill behavior.

## 3. Budget Sweep Reference (Why `35000` Decode + `20000` Prefill)

- `20000`: `2B@512` & `2B@2048` decode = `2.0 submits/tok`; `4B@512` prefill `p99 = 45.47 ms`, `4B@2048` prefill `p99 = 83.38 ms`.
- `32000`: `2B@512` & `2B@2048` decode still = `2.0 submits/tok`.
- `35000` unsplit (prior commit): `2B@512` & `2B@2048` decode = `1.0 submit/tok`, `4B` decode `p99 = 20.58 / 23.05 ms`, **but** `4B@512` prefill `p99` rose to `67.26 ms` and `4B@2048` prefill `p99` rose to `128.36 ms`.
- `40000` unsplit: same `1.0 submit/tok` on `2B` and `3.0 submits/tok` on `4B`, with higher `4B` decode `p99` (`24.35 / 26.08 ms`, `max = 31.50 ms`).
- **`{35000 decode, 20000 prefill}` (shipped here)**: keeps `2B` single-submit decode (`1.0 submit/tok`, `+1.30%` `5/5` wins) and `4B` decode `p99 <= 21.6 ms`, while holding `4B@512` all-submits `p99` at `45.60 ms` (`vs 45.34 ms`) and `4B@2048` all-submits `p99` at `83.31 ms` (`vs 83.04 ms`).

## 4. Unit Tests

`omarchy_runtime_tests -tc="*calibrated*,*work budget*"` passed (`2/2` test cases, `65/65` assertions), verifying:
- `calibrated_batch_work("Apple M1 (G13G B1)") == 35000` and `calibrated_prefill_batch_work("Apple M1 (G13G B1)") == 20000`.
- `batch_work_budget("Apple M1 (G13G B1)", false) == 35000` and `batch_work_budget("Apple M1 (G13G B1)", true) == 20000`.
- Sibling boards with `prefill_budget == 0` reuse their decode budget (`G13C == 80000`, `G14C == 200000`, `llvmpipe == 5000`).
- `is_prefill_work_kernel_name(...)` classifies multi-token prefill/tiled-matrix kernels (`QmmPrefill*`, `SdpaCausalFlash*`, `GatedDeltaPrefill*`, `Qmm{F32,F16,BF16}`, non-`MatmulVec` `Matmul*`) separately from 1-token decode kernels (`QmmVec*`, `SdpaDecode*`, `GatedDeltaDecode*`, `MatmulVec*`, `FastRmsNorm*`).
- Every row with `prefill_budget > 0` satisfies `prefill_budget <= budget`.
